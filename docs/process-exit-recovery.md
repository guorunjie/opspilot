# Abrupt Demo process exit: evidence and remaining work

Development update: async Demo snapshots expose a read-only recovery summary when a foreign shell/price claim exists or an idle handle sees EXECUTING/VERIFYING. The summary does not expose tokens or assert executor death. Renderer disables mutation controls while keeping saved evidence readable. Locally owned in-flight claims are not misreported as abandoned in command responses. The existing three child-exit tests assert this summary and its disappearance after supervised reconciliation; all 198 tests pass. Windows source desktop verification with a synthetic unreleased claim confirmed the visible banner, disabled mutation controls and unchanged SQLite rows/revisions. The screenshot was inspected. Four price scenarios, approval/submission reopen, supplemental normal flows and reset cancel/confirm also passed. This is an explanation of a blocked state, not a completed recovery action or authorization to unlock; packaged verification remains pending.

`test/asyncDemoProcessExit.test.js` runs a real Node child against a temporary SQLite database and exits it without application cleanup at three durable boundaries: Task EXECUTING saved, execution reservation saved, and synthetic target saved before acknowledgement. The parent requires the exact child's exit code before using the existing explicit abandoned-owner release API.

Both shell and price ownership survive. A reopened composition refuses execution and reset. Recovery without a termination confirmation is rejected. Once the test supervisor has confirmed termination, the lower-level price recovery transitions to UNKNOWN and independent readback yields FAILED for an unchanged target or VERIFIED for a matching target. Submission count stays respectively zero or one; the task cannot execute again. This is synthetic target verification, not a real platform result.

This test is not a desktop recovery feature, an OS power-loss test, or permission for users to edit ownership rows. The application still lacks a user-facing path to establish safe recovery authority. An elapsed timeout or a user's click alone cannot prove that a previous executor has stopped.

Next vertical slice must combine trusted application-instance ownership/termination evidence, a read-only interruption summary, explicit recovery confirmation, release of only the exact abandoned claims, UNKNOWN transition and readback, and continued rejection of duplicate execution. Cover a still-live competing instance, stale tokens, interrupted recovery itself and the separate reservation-before-START boundary. Preserve old archives and real-write isolation. Do not expose a generic unlock command to the renderer.

Local baseline after adding these tests: 195 tests passed. Packaged GUI recovery and real-store validation remain incomplete.

Development update: reservation now follows durable START, under the Agent's existing price ownership. A failed reservation checkpoint poisons the current handle; it cannot write or retry. Once that local operation has stopped, a reopened session can reconcile the unchanged target as FAILED, without submitting. Three abrupt child-exit cases and a reservation storage failure test pass; full local suite is 198 tests. This prevents new pre-START stranded reservations but does not migrate historical ones. Windows default source desktop regression passed all four price scenarios, approval/submission reopen, one submission per task, supplemental normal flows and reset cancel/confirm. A mismatch review viewport was visually checked. Immutable dev.4 installers are unchanged; packaged verification and user-facing recovery remain pending.

## Desktop instance prerequisite (development)

The desktop runtime now requests Electron's single-instance lock using a stable Core-only `desktop-runtime` userData directory under appData/opspilot-open-core, before readiness or opening SQLite. Browser sessionData remains a fresh temporary directory and the page uses a nonpersistent isolated partition. A rejected second launch exits before data access; the primary instance only restores/shows/focuses its window and ignores forwarded arguments. See [Electron app API](https://www.electronjs.org/docs/latest/api/app#apprequestsingleinstancelockadditionaldata).

196 local tests pass, including secondary-launch early exit and no mutation from forwarded arguments. Real Windows source Electron verification also passed: a second process exited normally, the primary received the second-instance event and restored its minimized window, forwarded execution arguments did not change the snapshot, and normal close/reopen reacquired the lock with the same snapshot. A viewport screenshot was inspected. Packaged and macOS two-process acceptance remain pending. This lock does not cover older binaries that never request it or arbitrary non-Electron writers, and is not sufficient evidence to release existing task claims. No automatic recovery or unlock was introduced. This development change is not included in the immutable dev.4 release.
